# Lesson03：UIコンポーネント開発とStorybookの役割

## はじめに

これまでの開発では、コンポーネントを作成しても **画面全体を表示しないと確認できない** 状態でした。

Storybookは、**コンポーネントを独立して開発・確認・ドキュメント化できるツール**です。

---

## Storybookとは

Storybookは、UIコンポーネントを **アプリケーションから切り離して** 個別に表示・テストできる開発ツールです。

### Storybookのメリット

1. **コンポーネント単体で確認できる**
   - 画面全体を表示しなくても、1つのコンポーネントだけを確認できる
   - 異なるpropsを渡した場合の表示をまとめて確認できる

2. **コンポーネントのカタログになる**
   - プロジェクト内のコンポーネントが一覧で見える
   - 新しいメンバーが「どんなコンポーネントがあるか」をすぐに把握できる

3. **ドキュメントとしても使える**
   - コンポーネントの使い方（props・バリエーション）が自然に文書化される

---

## Storybookの起動方法

Storybookがセットアップ済みのプロジェクトでは、以下のコマンドで起動できます。

```bash
npm run storybook
```

ブラウザが自動で開き、コンポーネントの一覧が表示されます（通常は `http://localhost:6006`）。

---

## ストーリーとは

Storybookでは、コンポーネントの **表示パターン** のことを **ストーリー（Story）** と呼びます。

例えば、ボタンコンポーネントの場合：

- Primary（メインカラー）のストーリー
- Secondary（サブカラー）のストーリー
- Danger（赤色・警告用）のストーリー
- Disabled（非活性）のストーリー

これらを1つのファイルにまとめて定義することで、コンポーネントのバリエーションを一覧で確認できます。

---

## Storybookが実務で使われる場面

### 1. コンポーネント設計の場面

新しいコンポーネントを作る際、まずStorybookで表示を確認しながら開発する「**コンポーネントファースト**」な開発スタイルが可能。

### 2. レビューの場面

「このボタン、こんな見た目ですがどうですか？」とStorybookのURLを共有して確認してもらえる。

### 3. デザインシステムの場面

プロジェクト全体で使う共通コンポーネント（ボタン・カード・モーダルなど）をStorybookで管理し、統一性を保つ。

---

## 本Lessonのまとめ

- Storybookは **コンポーネントを独立して開発・確認・ドキュメント化** するツール
- コンポーネントにさまざまなpropsを渡した時の表示をまとめて確認できる
- 実務ではコンポーネント設計・レビュー・デザインシステムの場面で活躍する
- 次のLessonでは、Storybookのストーリーの具体的な書き方を学びます
